# Pharmacy backend increment

Backend only; the original pharmacy/prescription screens remain previews until Section 4.

## Source review and intentional changes

Reviewed medicine and prescription model fields, prescription medicine fields, purchased medicine fields, PurchaseMedicineRepository stock receipt logic, PrescriptionRepository prescription/bill creation, and MedicineBillRepository stock checks. This is not a claim of complete source review or full prescription parity.

- Legacy medicines expose category, brand, composition, side effects, buying/selling prices and integer stock. The new catalog stores category/brand/unit labels; dedicated master records, edits/archive, supplier master records and complete purchase documents remain open.
- Legacy prescription lines include dosage, days, meal timing, frequency and comments. New signed medication orders require explicit dose, route, frequency, duration and dispensed-unit quantity. Quantity is never inferred from days times frequency, which cannot represent all dosing instructions correctly.
- A signed medication order is one medicine line linked to a real encounter. Full prescription document grouping, original history/vitals/meal fields, replacement versions and PDFs remain open.
- Only the assigned doctor signs; only the signing doctor cancels with a reason. Cancellation is a retained event and prevents further dispensing. Previously issued stock remains in history.
- Stock is consumed at actual dispensing, independently of payment status. Partial dispensing is allowed up to the prescribed quantity across all batches.
- Patient returns reference a specific dispensing record and cannot exceed its quantity. They remain quarantined and do not increase available stock or prescription allowance. Return assessment/disposal workflow and financial refunds are separate remaining work.
- No diagnosis, dose recommendation, substitution or blood compatibility decision is generated by this backend.

## API contracts

All routes require a Better Auth session and resolve the active database role. POST requires the configured Origin; unknown JSON fields and bodies over 32 KiB are rejected. Lists accept `page` (1..1000), with 25 records per page. These private Go routes are intentionally not added to the frontend proxy yet.

| Route | Input / result | Access |
|---|---|---|
| GET /v1/medicines | search, page; medicines array | admin, pharmacist, doctor |
| POST /v1/medicines | name, category, brand, unit, composition, sideEffects, sellingPriceMinor | admin, pharmacist |
| GET /v1/medicine-batches | medicineId, page; batches array | admin, pharmacist |
| POST /v1/medicine-batches | medicineId, lot, expiryDate, supplier, purchaseReference, unitCostMinor, quantity | admin, pharmacist |
| GET /v1/medication-orders | encounterId, page; orders array | admin/pharmacist; assigned doctor; owning patient |
| POST /v1/medication-orders | encounterId, medicineId, quantity, dose, route, frequency, durationDays, instructions | assigned doctor of active encounter |
| POST /v1/medication-orders/{id}/cancel | reason | signing doctor |
| GET /v1/pharmacy-movements | batchId, page; movements array | admin, pharmacist |
| POST /v1/pharmacy-movements | batchId, orderId, kind, quantity, originalId, reason | admin, pharmacist |

Receipt, signing and movement POSTs require an Idempotency-Key of 16..80 characters. Identical retries return the original record; changed payloads conflict. Cancellation retries with an identical reason succeed; a changed reason conflicts. `kind` accepts dispense, return or disposal. Receipt movements are generated only by the receipt transaction. Return requires originalId and a reason; disposal requires a reason and no orderId. Prices are ETB integer minor units; quantities are whole catalog units.

## Transaction invariants and evidence

Migration 006 creates relational catalog, batch, signed order, cancellation and movement records. Order locks serialize dispensing/cancellation; batch locks serialize depletion. Database checks disallow negative balances. Deferred triggers reconcile stored balances against append-only movements at commit, including receipt quantities. Batch metadata, signed medication content, cancellation events and movements cannot be updated/deleted through ordinary SQL.

The disposable-schema suite covers receipt/signing/dispensing/return retries, changed-key payload rejection, competing stock depletion, cross-batch prescribed limits, returned-stock quarantine, expiry, cancellation, wrong-doctor/patient/reception access, signed/stock mutation rejection, balance tampering, disposal, HTTP origin rejection and strict JSON. Unit tests check malformed quantities/relations, expiry and stock permissions across all nine roles. All Go tests and vet passed with database tests enabled.

## Pharmacy source billing (migration 007)

POST `/v1/pharmacy-movements/{id}/invoice` accepts `{accountId, discountBasisPoints}` and an Idempotency-Key. Only admin/accountant may issue financial invoices. Patient, quantity and unit price come from the actual dispensing record and cannot be supplied by the caller. Dispensing now captures the catalog sale price; historical records without a captured price are rejected instead of silently using a new price. Zero-value supply is not invoiced by this endpoint.

A transaction locks the dispensing source, snapshots the charge account and creates/seals the invoice plus an immutable unique source association. Concurrent requests with different keys return the same invoice when account/discount agree; altered terms conflict. Standard invoice payment/refund rules apply. Returning medicine does not automatically create a credit or initiate a refund; that linked financial correction workflow remains open.

Tests verify concurrent duplicate billing, price preservation after catalog edits, exact discounted total, pharmacist financial denial, patient invoice ownership, immutable source linkage and authenticated HTTP creation. Local migrations 005-007 applied successfully; the local API now runs `services/api/bin/api-pharmacy.exe`. The existing live integration suite and synthetic Chrome connected-workflow regression passed after the update. No new pharmacy frontend integration was added.
